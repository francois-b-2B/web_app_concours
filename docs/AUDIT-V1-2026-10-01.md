# Audit de la V1 — 1er octobre 2026

## Conclusion

Les calculs de base passent les vérifications effectuées. La priorité est de sécuriser les changements pendant un concours : corriger un score, modifier les inscriptions ou lancer les finales peut actuellement produire des incohérences. Une passe de stabilisation est recommandée avant de considérer la V1 comme figée.

Cet audit porte sur la copie locale. Il ne certifie pas l'absence de tout bug et ne prouve pas que la version actuellement déployée est identique. Aucun code applicatif, concours enregistré ou paramètre de production n'a été modifié. Seul ce rapport a été ajouté.

## Vérifications effectuées

- Lecture du code : authentification, inscriptions, tirage, poules, classement, finales, exports, affiche, QR code, contact, mode essai et schéma de données.
- Tests existants : **28 tests réussis dans 4 fichiers**.
- Vérification TypeScript : **aucune erreur**.
- Simulations supplémentaires avec les fonctions réelles : **123 effectifs, de 6 à 128 équipes**. Répartition sans omission ni doublon, rencontres distinctes, absence de double participation dans une ronde et progression du tableau jusqu'au vainqueur sur les scénarios simulés.
- Génération d'exports XLSX, XLS, ODS, CSV et PDF avec des données fictives.
- Reproduction de corrections de scores avec les vraies actions serveur et une base simulée en mémoire.
- Vérification du parcours essai dans un onglet séparé, sans sauvegarde.
- Analyse ESLint et audit des dépendances de production.

La couverture automatique existante concerne surtout les algorithmes. Elle ne couvre pas suffisamment les transitions entre étapes, la persistance et les exports. Les connexions Google externes, l'envoi réel d'e-mails, la restauration d'une sauvegarde et l'affichage sur un véritable iPhone n'ont pas été retestés dans cet audit.

## Corrections prioritaires

### 1. Une correction de résultat peut rendre les finales incohérentes — confirmé par reproduction

**Exemple reproduit :** A gagne une demi-finale puis la finale. On corrige la demi-finale : B était le gagnant. Le participant de la finale devient B, mais son ancien score et le vainqueur A restent enregistrés. Si la demi-finale devient une égalité, le participant déjà envoyé en finale n'est pas retiré.

Le même défaut de propagation apparaît dans le code du mode essai. En version connectée, remettre une finale à rejouer ne rétablit pas non plus le statut du concours, qui peut rester terminé.

**À faire :** encadrer la correction et invalider les résultats dépendants, avec une confirmation si des tours suivants ont déjà été joués.

Repères : `src/app/tournaments/[id]/bracket/actions.ts:139` ; `src/app/essai/page.tsx:267`.

### 2. Les finales peuvent être lancées avant la fin des poules — confirmé

Reproduit dans le navigateur en mode essai : **0 match sur 12 joué**, mais le tableau final se crée. L'action serveur connectée ne vérifie pas davantage que les poules sont terminées. Les qualifications peuvent donc être figées à partir d'un classement provisoire. Les scores des poules restent ensuite modifiables sans recalcul du tableau final.

**À faire :** bloquer le lancement tant que des résultats requis manquent, puis définir comment gérer les corrections après qualification.

Repères : `src/app/tournaments/[id]/bracket/actions.ts:30` ; `src/app/tournaments/[id]/pools/[letter]/actions.ts:34`.

### 3. Les inscriptions restent modifiables après le tirage — confirmé dans le code

En version connectée :

- Une nouvelle équipe peut être ajoutée, mais n'entre dans aucune poule ; un second tirage est refusé.
- Le retrait d'une équipe engagée dans des matchs se heurte aux contraintes de la base, sans message métier prévu.

En mode essai, ajouter, retirer ou simplement renommer une équipe efface les poules, les matchs et les finales. Une correction de nom peut donc faire perdre toute la simulation.

**À faire :** autoriser les corrections de nom/contact sans perdre les résultats ; encadrer séparément les changements de composition après tirage. La suppression d'un concours reste une autre opération.

Repères : `src/app/tournaments/[id]/teams/actions.ts:31` et `:125` ; migration initiale, contraintes PoolMatch ; `src/app/essai/page.tsx:167` et `:284`.

### 4. Le plafond des finales contredit la règle annoncée pour les grands concours — confirmé par simulation

L'interface promet les deux premiers de chaque poule. Avec **128 équipes, le calcul crée 42 poules**, donc 84 équipes devraient bénéficier de cette règle. Or le tableau final est plafonné à **64 places**.

**À décider :** agrandir le tableau ou revoir explicitement la règle de qualification et le texte affiché. Les calculs ne peuvent pas garantir simultanément ces deux contraintes.

Repères : `src/lib/tournament/bracket.ts:15` ; `src/app/tournaments/[id]/bracket/page.tsx:54`.

### 5. La recréation de la base n'est pas reproductible avec les migrations seules — confirmé dans les fichiers

Le schéma actuel prévoit un identifiant unique et un e-mail facultatif. Les migrations conservées créent encore un utilisateur sans colonne `username`, avec un e-mail obligatoire. Aucune migration corrective correspondante n'a été trouvée.

Cela ne démontre pas un défaut de la base actuelle, qui a pu être adaptée autrement. En revanche, une nouvelle installation utilisant uniquement les migrations ne correspondrait pas au code.

**À faire :** préparer et vérifier la migration manquante sur une base de test avant toute application à la production.

Repères : `prisma/schema.prisma:12` ; `prisma/migrations/20260918182257_init/migration.sql:20`.

## Autres anomalies et limites

| Sujet | Constat et preuve | Suite proposée |
|---|---|---|
| PDF | Reproduction : un document d'une page passe à deux pages au moment d'écrire « Page 1 / 1 ». Le pied de page est placé trop bas, à y=810. | Corriger la pagination et vérifier un export long. |
| Contact d'une équipe | Vider le champ produit `undefined`, ignoré par Prisma : l'ancienne valeur n'est pas effacée. | Envoyer explicitement une valeur vide ou null. |
| Équipes d'exemple | Le bouton annonce « 9 ou 10 », mais ajoute **8 équipes**, confirmé dans le navigateur. | Aligner le nombre et le libellé. |
| Capacité en essai | Le compteur affiche /128, mais l'ajout ne contrôle pas ce plafond. | Harmoniser les validations. |
| Affiche personnalisée | Les champs sont conservés dans l'état du composant seulement. Quitter/recharger la page fait perdre la personnalisation, même connecté. | Décider si l'affiche doit être sauvegardée avec le concours. |
| Scores extrêmes | Les contrôles acceptent tout entier positif, sans plafond compatible avec un entier PostgreSQL. | Refuser proprement les valeurs excessives. |
| Export CSV | Un nom fictif `=1+1` reste tel quel dans le CSV. Certains tableurs peuvent l'interpréter comme une formule. | Neutraliser les cellules textuelles commençant comme une formule. |

Repères : `src/lib/export/tournament-export.ts:346` ; `src/app/tournaments/[id]/teams/actions.ts:98` ; `src/app/essai/page.tsx:34` et `:360` ; `src/app/tournaments/[id]/poster/poster-editor.tsx:51`.

## Sécurité et dépendances

Points positifs : les opérations sensibles examinées contrôlent le propriétaire du concours ; les mots de passe sont hachés avec bcrypt ; les exports connectés exigent une authentification. Ces constats ne remplacent pas un test d'intrusion.

L'audit npm signale **5 paquets affectés : 1 alerte critique et 4 élevées**. Ce ne sont pas cinq failles distinctes dont l'exploitation aurait été démontrée dans cette application :

- **Next.js 16.3.5** : alerte critique concernant `next/og ImageResponse`. Aucun usage de cette fonctionnalité n'a été trouvé dans le code applicatif. Une mise à jour corrective reste recommandée. L'avis indique un correctif à partir de 16.3.6 pour cette branche. [Avis de sécurité Next.js](https://github.com/advisories/GHSA-vcvr-r3jv-pc5j).
- **SheetJS/xlsx 0.18.5** : alertes liées notamment à la lecture de fichiers malveillants. L'application écrit des exports, sans import de classeur trouvé ; l'exposition aux scénarios décrits est donc différente. Prévoir une distribution corrigée ou une alternative maintenue. [Prototype pollution](https://github.com/advisories/GHSA-4r6h-8v6p-xvw6), [déni de service](https://github.com/advisories/GHSA-5pgg-2g8v-p4x9).
- **deepmerge-ts via Prisma** : alerte sur une dépendance transitive, comptabilisée aussi dans ses dépendants. Aucun scénario d'exploitation applicatif reproduit. Vérifier la mise à jour de la chaîne Prisma sans appliquer aveuglément les propositions automatiques.

Aucune limitation applicative des tentatives de connexion, de création de comptes et d'envoi de messages n'a été trouvée. Des protections d'hébergement peuvent exister ; elles n'ont pas été auditées. Un contrôle explicite réduirait les risques d'abus.

## Optimisation et code devenu inutile

1. **Image d'affiche très lourde : environ 36 Mo.** Elle est directement référencée dans l'éditeur et l'aperçu essai. Prévoir une version légère pour l'écran et réserver la haute définition à l'export. Son poids ne concerne pas systématiquement chaque visite de l'accueil.
2. **Ancienne affiche d'environ 35 Mo sans référence trouvée.** Candidate au retrait après vérification des éventuels usages externes.
3. **Ancien export du mode essai encore présent**, alors que les téléchargements sont désactivés : fonctions `exportCompetition`, `exportSheets`, `downloadFile` et état associé. Nettoyage possible. Ne pas supprimer la dépendance jsPDF globalement : l'affiche connectée l'utilise encore.
4. **Calcul du contenu de tous les onglets essai à chaque rendu**, même lorsqu'un seul onglet est affiché. Ne construire que le contenu actif et partager davantage de composants avec la version connectée.
5. **Dossiers de compilation volumineux** : environ 471 Mo pour `.next-production`, 287 Mo pour `.next`, 5 Mo pour `.next-local`. Les exclusions spécifiques des variantes locales sont à compléter et la liste des fichiers envoyés au déploiement à contrôler. Ces chiffres sont des tailles disque, pas le poids téléchargé par les visiteurs.
6. Quelques SVG de démarrage Next.js ne présentent pas de référence applicative trouvée.
7. **ESLint : 6 erreurs et 3 avertissements** sur le périmètre contrôlé. Cinq erreurs concernent l'usage CommonJS valide du script de sauvegarde sous une règle ESLint inadaptée ; la sixième concerne un setState dans un effet de l'éditeur d'affiche. Les avertissements concernent notamment l'export essai inutilisé et une image QR. Ces résultats ne signifient pas neuf pannes fonctionnelles.

## Ordre recommandé

1. Fiabiliser scores, qualifications et changements d'inscriptions ; ajouter les tests de régression associés.
2. Régler la limite du tableau final et la migration des comptes.
3. Corriger PDF, contact effaçable et incohérences du mode essai.
4. Mettre à jour les dépendances et ajouter les protections contre les abus.
5. Alléger les images, supprimer le code inutilisé et compléter les tests de parcours.
6. Valider les changements sur une base isolée, puis effectuer une vérification mobile réelle avant publication.

Il n'est pas nécessaire de réécrire l'application : les défauts principaux sont localisés, mais ils touchent des situations importantes pendant un concours.
